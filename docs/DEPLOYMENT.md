# Deployment guide

Target layout (one registrable domain, three hosts):

| Host | Component | Platform |
|---|---|---|
| `osasweather.com` | `weather-app/` | Vercel project 1 |
| `admin.osasweather.com` | `admin-app/` | Vercel project 2 |
| `api.osasweather.com` | `backend/` + PostgreSQL | Render |

Use your own domain in place of `osasweather.com` throughout. Nothing here has been deployed or verified on live hosting yet. Treat every step as a checklist to test.

## 0. Push to GitHub

Create a repository named `OsasWeather` and push the whole folder. `.env` files are ignored; only `backend/.env.example` is committed. Confirm with `git status` that no secrets are staged.

## 1. Render: database and API

1. **Blueprint route:** Render dashboard, *New*, *Blueprint*, choose the repo. It reads `render.yaml` and creates `osasweather-db` (PostgreSQL 16) and `osasweather-api`. Adjust plans and region in the file first (the free database tier expires).
   **Manual route:** create a PostgreSQL instance, then a *Web Service* with root directory `backend`, build `npm ci --omit=dev`, start `npm run migrate && npm start`, health check `/api/health`.
2. Set the environment variables the blueprint marks `sync: false`:
   * `FRONTEND_URL=https://osasweather.com` and `ADMIN_FRONTEND_URL=https://admin.osasweather.com` (exact origins, no trailing slash, https).
   * `ALLOWED_ORIGINS=https://osasweather.com,https://admin.osasweather.com,https://osasweather-preview.vercel.app` (comma-separated list of all allowed origins for CORS and CSRF).
   * `EMAIL_*` (step 4). `SESSION_SECRET`, `ADMIN_SESSION_SECRET`, `CSRF_SECRET` are generated by the blueprint. If you create them manually, use three **different** random values of 32+ characters (`node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`). In production the API refuses to start otherwise.
3. Add the custom domain `api.osasweather.com` to the service and create the DNS record Render shows.
4. Confirm `https://api.osasweather.com/api/health` returns `{"success":true,...,"database":"up"}`. Migrations run automatically on every start (safe: transactional, idempotent, lock-protected).

## 2. Create the single owner account (once)

Never through a web page. Choose one:

* **Render Shell** (if your plan includes it), in the `osasweather-api` service:
  `OWNER_ADMIN_EMAIL=you@example.com OWNER_BOOTSTRAP_SECRET=<24+ random chars> npm run bootstrap-owner`
  You are prompted for the secret and a hidden password (12+ chars with a letter and a number).
* **From your own machine** against production: set `DATABASE_URL` to the database's **external** connection string and `DATABASE_SSL=true`, then run the same command in `backend/`.

The command is idempotent: if an owner exists it changes nothing, and the database itself rejects a second administrator. Never leave `OWNER_BOOTSTRAP_SECRET` or `OWNER_INITIAL_PASSWORD` set in the service environment afterwards.

## 3. Vercel: two projects from the same repository

For each project: *Add New Project*, import the repo, then:

| Setting | `weather-app` project | `admin-app` project |
|---|---|---|
| Root Directory | `weather-app` | `admin-app` |
| Framework Preset | Other | Other |
| Environment variable | `API_BASE_URL=https://api.osasweather.com` | `API_BASE_URL=https://api.osasweather.com` |
| Domain | `osasweather.com` | `admin.osasweather.com` |

`vercel.json` supplies the build command (`node build-config.js`, which writes the API address into `assets/js/config.js` and refuses non-https in production), headers, caching and the admin `/` rewrite. If your API host differs, edit `connect-src` in both `vercel.json` files.

Also replace the host in `weather-app/robots.txt` and `weather-app/sitemap.xml`.

**Protect the admin site.** Backend authorization is the real protection, but also put an access gateway in front of the admin deployment (Vercel Deployment Protection if your plan offers it, Cloudflare Access, or an IP allow-list). Do not rely on the URL being secret.

## 4. Email (password reset and email change)

Choose an SMTP provider (for example Brevo, Mailgun, Amazon SES, Resend SMTP, or your own). Verify your sender domain (SPF/DKIM) with them, then set `EMAIL_HOST`, `EMAIL_PORT` (587 + `EMAIL_SECURE=false` for STARTTLS, or 465 + `true`), `EMAIL_USER`, `EMAIL_PASSWORD`, `EMAIL_FROM`. The admin System section shows "Email provider: Configured" once the variables are present, which does **not** prove delivery. Test the real flow: request a reset for your own address and open the link. Without these variables no email is sent at all.

## 5. Post-deployment verification (do all of these in real browsers)

1. Public site loads; landing preview shows a live forecast (this is your first live Open-Meteo call; check the admin API monitoring page shows successes, not `UPSTREAM_ERROR`).
2. Register, log in, log out; confirm in DevTools that the only cookie is `osw_sid` with `HttpOnly`, `Secure`, `SameSite=Lax` on `api.` host (host-only, no `Domain`).
3. Test in Chrome, Safari (including iOS) and Firefox: login persistence after refresh, favourites, settings, theme persisted across two devices.
4. Forgot-password email arrives and the link works once only.
5. Admin: sign in on `admin.`; confirm `osw_admin_sid` is a separate cookie; confirm a signed-in ordinary user visiting the admin site is sent back to its sign-in page.
6. Suspend a test user in the admin console and confirm their open public session ends at once; reactivate.
7. Confirm no link to the admin site exists anywhere on the public site (view source, footer, menus).
8. `curl -I` both sites and confirm the CSP, `X-Frame-Options`, and (admin) `X-Robots-Tag` headers.
9. Run a Lighthouse / WebPageTest pass on a throttled mobile profile and compare with the figures in the README.

## 6. Operations

* **Backups:** enable Render's database backups and test a restore.
* **Retention:** `api_request_logs`, `system_error_logs`, `admin_activity_logs` and expired sessions grow. Schedule a cleanup (for example monthly, delete `api_request_logs` and `system_error_logs` older than 90 days).
* **Scaling:** the rate limiter and weather cache are in-memory. For multiple API instances use a shared store.
* **Secrets rotation:** changing `SESSION_SECRET` / `ADMIN_SESSION_SECRET` signs everyone out (acceptable); changing `CSRF_SECRET` invalidates current tokens (clients refetch automatically).
* **Legal:** replace the placeholder `terms.html`, add a privacy policy, and review Open-Meteo's licence terms for commercial use.
